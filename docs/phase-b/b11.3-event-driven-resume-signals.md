# B11.3 — Event-Driven Resume & Callback Governance

B11.3 introduces an idempotent orchestration signal inbox.

Signals:
- EXECUTION_RELEASED
- ADAPTER_ACTIVATED
- NATIVE_DRAFT_CONFIRMED
- NATIVE_RECORD_CREATED
- RECOVERY_REQUESTED

A signal never proves a governance action occurred. Before resuming a run the
runtime independently reads persisted Enorsis state and verifies the relevant
gate:

- RELEASED_HANDOFF -> execution envelope must be RELEASED and have
  releasedByUserId
- ADAPTER_PREPARED -> adapter must record activatedByUserId and be in an
  activated/materialized/completed state
- NATIVE_DRAFT_MATERIALIZED -> governed native draft must exist

Signals are idempotent by tenant + idempotencyKey.

Endpoints:
POST `/api/automation/autonomous-orchestration/signals`
GET/POST `/api/automation/autonomous-orchestration/signals/process`

Both endpoints use the existing `CRON_SECRET` Bearer authorization pattern.
