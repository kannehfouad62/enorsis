# B13.10.15 — Reliable Commerce Notifications & Procurement-to-Warehouse Handoff

## Notification reliability

Root cause:
`createEnterpriseNotification()` created notification and delivery rows, but
actual IN_APP/EMAIL delivery depended on the asynchronous pending-delivery
processor.

B13.10.15 adds targeted immediate processing:

`createAndDeliverEnterpriseNotification()`

Commerce notifications now:
1. persist the canonical notification,
2. create delivery rows,
3. immediately claim/deliver those rows,
4. retain the existing retry/dead-letter behavior if delivery fails.

Applied to:
- selected approver notification
- requester marketplace notifications
- seller-tenant order notifications
- approval escalation notifications
- supplier acceptance notifications
- supplier shipment notifications

## Supplier acceptance -> warehouse handoff

When a seller accepts a marketplace order:
- buyer requester is notified,
- buyer receiving/procurement stakeholders are notified,
- the seller-order line snapshot becomes available to Warehouse Operations,
- an AuditEvent records that the accepted order entered receiving readiness.

When shipped:
- tracking/carrier notification goes to the requester,
- receiving stakeholders receive an inbound-shipment notification,
- the same accepted product remains available in Warehouse Operations.

## Warehouse receiving

`/app/warehouse-operations`

New section:

**Marketplace accepted orders**

The dropdown contains product lines from buyer-owned MarketplaceSellerOrder rows
whose status is ACCEPTED or SHIPPED.

Selecting a product prefills:
- seller order number
- marketplace seller order ID
- Purchase Request link context
- Purchase Order Execution ID
- buyer-side supplier projection ID
- seller tenant/name
- product name
- SKU/source line reference
- expected quantity
- UOM
- carrier
- tracking number
- expected delivery date

The warehouse receiver supplies/validates physical facts:
- buyer inventory item ID
- actual received quantity
- condition
- serial/batch/lot reference
- dock/staging location

This deliberately separates commercial/order master data from physical-receipt
evidence.

## Existing warehouse chain remains authoritative

The bridge feeds the existing flow:

Accepted Marketplace Order
-> Warehouse Receiving Session
-> Receipt Line
-> Discrepancy detection where applicable
-> Putaway Task
-> Putaway completion
-> Inventory movement ledger
-> Inventory availability snapshot

It does not create a fake receipt merely because the supplier clicked Accept.

## Auditability

Supplier acceptance handoff:
`marketplace.order.accepted_for_receiving`

Physical marketplace receipt:
`warehouse.marketplace_receiving.recorded`

The latter records product/source, expected vs received quantity, condition,
serial/lot, supplier, PO execution, carrier and tracking references.

These events are searchable in the governed Activity Log.
