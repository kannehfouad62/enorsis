# B13.10.5 — Marketplace Cart, Governed Purchase Request & Automated Commerce Orchestration

B13.10.5 adds a buyer marketplace cart as an orchestration layer over existing
Enorsis procurement modules. It does not replace Purchase Requests, approvals,
Purchase Orders, receiving, warehouse, inventory, invoice, three-way match or
payment readiness.

Buyer flow:
Marketplace Catalog -> Add to Cart -> Purchase Cart -> existing PR fields ->
canonical PurchaseRequest -> governed approval.

The server re-queries each marketplace offering at checkout. Price, seller
identity, availability, MOQ and commercial data are not trusted from local
browser cart state.

A MarketplacePurchaseRequestLineBinding stores the immutable marketplace
snapshot and seller tenant/supplier provenance for every canonical PR line.

Approval routing continues to use the existing APPROVER membership and
approvalLimitUsd chain. The current Enorsis model does not establish a provable
direct-manager reporting line, so B13.10.5 does not fabricate one.

Rejected/returned PR:
- requester gets in-app + email notification
- seller gets no order and no notification

Approved PR:
- lines are grouped by seller tenant
- one supplier-specific RTO journey and one PO are generated per seller
- buyer-side supplier projections preserve tenant isolation
- the existing create -> validate -> issue PO services are used
- seller gets in-app + email notification

Seller Marketplace Orders:
- Accept -> existing PO acknowledged, buyer notified
- Reject -> RTO exception raised, buyer notified
- Ship -> carrier/tracking stored, buyer notified and directed to Goods Receipt

Goods receipt, warehouse putaway, inventory posting, invoice, three-way match
and payment readiness remain real downstream controls and are not auto-completed.
